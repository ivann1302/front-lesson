# API и SQLite

API использует Fastify, Drizzle ORM и локальный SQLite-файл. При старте выполняются версионные
SQL-миграции, после чего 60 материалов загружаются через идемпотентный upsert.

## Команды

```bash
corepack pnpm@9.15.4 dev:api
corepack pnpm@9.15.4 db:seed
```

По умолчанию файл создаётся как `apps/api/data/mentor.db`, если команда запускается через
workspace script. Путь можно изменить через `DATABASE_URL`.

## Реализованные маршруты

### `GET /health`

Проверяет доступность API и реальный запрос к SQLite. Не возвращает конфигурацию или секреты.

### `POST /auth/guest`

Создаёт гостя и возвращает случайный `guestToken`. Повторный запрос с этим токеном восстанавливает
того же пользователя. Timezone принимается только в формате IANA.

```json
{
  "timezone": "Europe/Moscow"
}
```

### `POST /auth/telegram-code`

Требует заголовок `x-guest-token`. Создаёт новый восьмизначный код привязки со сроком жизни
10 минут; предыдущий код этого пользователя становится недействительным. В SQLite сохраняется
только SHA-256-хеш кода.

```json
{
  "code": "ABCD2345",
  "expiresAt": "2026-07-16T12:30:00.000Z"
}
```

### `POST /auth/telegram-link`

Внутренний маршрут для Telegram-бота. Требует общий секрет в заголовке
`x-telegram-internal-secret` и принимает код вместе со строковым Telegram user id:

```json
{
  "code": "ABCD2345",
  "telegramUserId": "123456789"
}
```

Успешный запрос атомарно создаёт Telegram identity, включает канал уведомлений и погашает код.
Код нельзя использовать повторно, а один Telegram-аккаунт нельзя привязать к двум пользователям.
API и бот должны получать одинаковый `TELEGRAM_INTERNAL_SECRET` длиной не менее 32 символов.

### `POST /bot/study/today`

Внутренний маршрут команды Telegram `/today`. Требует `x-telegram-internal-secret` и принимает
строковый идентификатор уже привязанного Telegram-пользователя:

```json
{
  "telegramUserId": "123456789"
}
```

Возвращает ту же стабильную дневную сессию, что `GET /study/today`, но в компактном формате:
прогресс и первый незавершённый материал. Для задания с вариантами может вернуть публичные
`options`, но вместо content/option id каждая кнопка получает короткий непрозрачный
`callbackData`. Правильный ответ и объяснение не возвращаются. Непривязанный Telegram id получает
`404 TELEGRAM_IDENTITY_NOT_FOUND`.

### `POST /bot/answers`

Внутренний маршрут inline single-choice. Требует `x-telegram-internal-secret` и принимает Telegram
user id вместе с `callbackData`, который ранее выдал `/bot/study/today`:

```json
{
  "telegramUserId": "123456789",
  "callbackData": "answer:AbCdEfGh1234"
}
```

Callback содержит 72-битный случайный токен, живёт 24 часа и на сервере связан с пользователем,
сессией, материалом, вариантом и стабильным `clientAnswerId`. Поэтому повтор того же callback
возвращает прежний результат без второй записи, callback другого пользователя не раскрывается, а
нажатие другой кнопки после сохранённого ответа получает `409 ALREADY_ANSWERED`.

Ответ содержит correctness, объяснение и прогресс сессии. Сохранение выполняет тот же сервис и ту
же транзакцию, что публичный `POST /answers`.

### `POST /bot/settings`

Возвращает Telegram-пользователю серверные настройки того же профиля: выбранные темы, дневной
лимит, локальное время, IANA timezone, дни недели, канал и `pausedUntil`. Требует внутренний секрет
и тело `{ "telegramUserId": "123456789" }`.

### `POST /bot/settings/pause`

Ставит уведомления на паузу или возобновляет их. Не блокирует обучение и не меняет дневную очередь:
обновляется только `notification_settings.paused_until`.

```json
{
  "telegramUserId": "123456789",
  "action": "day"
}
```

Допустимые действия: `day` — 24 часа, `week` — 7 дней, `resume` — снять паузу. Ответ возвращает
полное актуальное состояние настроек, поэтому бот сразу подтверждает результат пользователю.

### `GET /study/today`

Требует заголовок `x-guest-token`. Один раз фиксирует дневную очередь из просроченных повторений
и новых материалов в пределах `dailyLimit`. Повторный запрос в тот же локальный день возвращает
ту же сессию. Объект `session` содержит `answered` и `total`, а каждый материал — свой `status`,
поэтому web-клиент восстанавливает прогресс после перезагрузки.

До ответа пользователя API намеренно удаляет `correctOptionIds`, `answer`, `definition`,
`explanation`, `solution`, `rubric` и `referencePoints`.

### `POST /answers`

Требует заголовок `x-guest-token`. Принимает UUID с клиента, проверяет принадлежность задания
дневной или practice-сессии, сохраняет ответ и в одной транзакции обновляет статус задания, сессию и
`user_content_state`.

Для заданий с вариантами:

```json
{
  "clientAnswerId": "5f2ca37f-218b-49de-910b-8c2bb0207d3c",
  "sessionId": "ef8d31d4-41f2-42ae-8e66-c6376e0425e6",
  "contentId": "js-array-map-003",
  "answer": { "kind": "selection", "selectedOptionIds": ["a"] },
  "latencyMs": 1250
}
```

Для `code_output` используется `{ "kind": "text", "text": "..." }`. Термины, карточки,
поиск ошибки и открытые интервью-вопросы оцениваются пользователем через
`{ "kind": "self_assessment", "rating": "again|hard|good|easy" }`; к самооценке можно
добавить поле `text` с черновиком ответа.

Ответ API содержит результат проверки, раскрытые только после отправки правильный ответ и
объяснение, новый интервал с `nextDueAt`, а также прогресс сессии. Объективные форматы
`single_choice`, `multiple_choice` и `code_output` проверяются сервером. Для остальных форматов
`isCorrect` равен `null`, а расписание определяется самооценкой.

Повтор полностью того же запроса с прежним `clientAnswerId` возвращает сохранённый результат со
статусом `200` и не меняет расписание второй раз. Использование этого UUID для другого ответа
возвращает `409 IDEMPOTENCY_CONFLICT`. Второй ответ на уже закрытое задание с новым UUID также
возвращает `409`.

### `GET /settings`

Возвращает состояние onboarding и текущий учебный план: выбранные темы, дневной лимит, локальное
время напоминания и IANA timezone. Для нового гостя по умолчанию выбраны все шесть тем, пять
заданий и `19:00` в часовом поясе браузера.

### `PUT /settings`

Требует заголовок `x-guest-token` и полностью заменяет учебные настройки пользователя:

```json
{
  "topics": ["javascript", "typescript", "react"],
  "dailyLimit": 3,
  "localTime": "19:30",
  "timezone": "Europe/Moscow"
}
```

Нужно выбрать от одной до шести уникальных тем; `dailyLimit` ограничен диапазоном 1–5. Время и
timezone проходят серверную проверку. Пользователь, настройки уведомлений и темы обновляются в
одной транзакции. Новая дневная очередь учитывает выбранные темы, но уже созданная сессия на
текущий локальный день намеренно остаётся неизменной.

### `GET /stats`

Требует заголовок `x-guest-token` и строит статистику только из сохранённых ответов и сессий:

- общий объём ответов и отдельно количество объективно проверяемых заданий;
- точность, число завершённых дневных сессий и текущая серия;
- просроченные повторы и ближайшая дата повторения;
- попытки, объективная точность, среднее время ответа и повторы по выбранным темам;
- активность за последние семь локальных дней пользователя.

Самооценки карточек и интервью-вопросов входят в количество практики, но не в процент
правильных ответов. Серия сохраняется, если последняя завершённая сессия была сегодня или вчера
в timezone пользователя.

### `GET /learning`

Требует заголовок `x-guest-token`. Возвращает публичный каталог из 60 материалов, сводку по
шести темам и пользовательское состояние каждого материала: `new`, `learning`, `due` или
`mastered`. Правильные ответы и объяснения до тренировки не раскрываются.

### `GET /theory`

Требует заголовок `x-guest-token`. Возвращает каталог теоретических глав без полного текста:
`id`, тему, slug, заголовок, краткое описание и расчётное время чтения. В `summary` находятся
счётчики начатых, прочитанных и добавленных в закладки глав, а `completionPercent` — округлённую
долю прочитанных от полного каталога. Каждый элемент содержит отдельное пользовательское состояние:

```json
{
  "articleId": "ts-generics-001",
  "status": "completed",
  "bookmarked": true,
  "lastOpenedAt": "2026-07-17T10:30:00.000Z",
  "completedAt": "2026-07-17T10:35:00.000Z"
}
```

Для ещё не открытой главы API вычисляет состояние `new`, `false` и две даты `null`, не создавая
лишнюю строку в базе.

### `GET /theory/:articleId`

Требует заголовок `x-guest-token`. Возвращает полную валидированную главу: разделы, оригинальные
примеры кода, объяснения, ключевые тезисы, ссылки на источники, `relatedContentIds` для запуска
practice-сессии и тот же объект `state`, что каталог. Связанные ID проверяются при сборке контента,
но не входят в краткий ответ каталога. Неизвестный ID получает `404 THEORY_ARTICLE_NOT_FOUND`.

### `PUT /theory/:articleId/state`

Идемпотентно сохраняет состояние главы текущего гостя. Можно передать статус, флаг закладки или
оба поля:

```json
{
  "status": "completed",
  "bookmarked": true
}
```

Записываемые статусы — `reading` и `completed`; `new` существует только как вычисляемое состояние
для главы без записи. После `completed` повторная отправка `reading` не понижает прогресс, а
`completedAt` сохраняет время первого завершения. Изменение закладки не меняет статус уже
прочитанной главы. Пустое или неизвестное поле получает `400 VALIDATION_ERROR`.

### `POST /study/practice`

Создаёт отдельную тренировку из 1–10 уникальных `contentIds` и возвращает её в том же публичном
формате, что дневная сессия. За день можно создать несколько practice-сессий; они обновляют
прогресс материалов и общую статистику ответов, но не меняют дневную очередь и серию дней.

### `GET /study/practice/:sessionId`

Восстанавливает принадлежащую гостю practice-сессию после перезагрузки страницы: сохранённый
прогресс, исходный порядок и только публичные поля материалов. Чужой или неизвестный ID получает
`404 PRACTICE_SESSION_NOT_FOUND`, поэтому наличие сессии другого пользователя не раскрывается.

### `GET /mock-interviews`

Требует заголовок `x-guest-token`. Возвращает шесть наборов с названием, направлением, описанием,
рекомендуемой длительностью и количеством вопросов. Сами вопросы и эталонные тезисы каталог не
раскрывает.

### `POST /mock-interviews/sessions`

Создаёт mock-интервью выбранной длительности и сразу возвращает первый публичный вопрос:

```json
{
  "setId": "mock-react",
  "durationMinutes": 30
}
```

Допустимы 15, 30 или 45 минут. `endsAt` рассчитывается сервером; клиентский таймер отображает это
значение, но не определяет фактический статус сессии. До открытия разбора публичный вопрос
содержит prompt, tags, оценочное время, позицию, пустые `notes` и `revealed: false` — поле
`referencePoints` отсутствует.

### `GET /mock-interviews/sessions/:sessionId`

Восстанавливает принадлежащую гостю сессию и текущий вопрос вместе с сохранёнными тезисами и
состоянием разбора. Эталонные тезисы возвращаются только для уже открытого вопроса. Ответ также
содержит счётчики `assessedQuestions` и `weakQuestions`. Если серверное время уже достигло
`endsAt`, запрос атомарно завершает сессию с причиной `timeout`. Чужой или неизвестный UUID
возвращает `404`, не раскрывая владельца.

### `GET /mock-interviews/history`

Возвращает до 20 последних завершённых сессий текущего гостя в обратном хронологическом порядке.
Для каждой сессии доступны набор, дата, причина завершения и количество оценённых и слабых
ответов. Поле `analytics` содержит сводные показатели по этой выборке, хронологический тренд
последних восьми сессий и шесть самых частых тегов слабых ответов. `confidencePercent` — доля
оценок `good` и `easy` среди оценённых ответов; при отсутствии оценок возвращается `null`.
Активные сессии и содержимое вопросов в список не попадают.

### `GET /mock-interviews/sessions/:sessionId/report`

Возвращает детальный отчёт завершённой сессии: сохранённые тезисы, самооценку, эталонные пункты и
признак добавления связанных материалов в повторение. В отчёте присутствуют только вопросы, для
которых пользователь открывал разбор. Активная сессия получает
`409 MOCK_INTERVIEW_SESSION_ACTIVE`, чужая или неизвестная — `404`.

### `POST /mock-interviews/sessions/:sessionId/practice`

Создаёт отдельную practice-сессию из уникальных учебных материалов, связанных с ответами
`again` и `hard` в завершённом интервью. Порядок определяется вопросами исходного набора, размер
ограничен десятью материалами. Внутренние связи вопросов клиенту не передаются. Если слабых тем
нет, endpoint возвращает `409 MOCK_INTERVIEW_NO_WEAK_TOPICS`; для активной сессии —
`409 MOCK_INTERVIEW_SESSION_ACTIVE`.

### `POST /mock-interviews/sessions/:sessionId/reveal`

Принимает `{ "questionId": "...", "notes": "тезисы ответа" }`, сохраняет до 5000 символов и
открывает `referencePoints` только текущего вопроса. Повтор запроса идемпотентно обновляет тезисы,
пока вопрос ещё не оценён. Открытый разбор и тезисы восстанавливаются после перезагрузки.

### `POST /mock-interviews/sessions/:sessionId/next`

Принимает `{ "questionId": "...", "rating": "again|hard|good|easy" }` после открытия разбора и
только затем открывает следующий вопрос набора. Сервер сверяет ID с текущей позицией; попытка
перескочить или отправить другой вопрос получает `409 MOCK_INTERVIEW_QUESTION_MISMATCH`, а оценка
до разбора — `409 MOCK_INTERVIEW_REVIEW_REQUIRED`. Оценки `again` и `hard` планируют ближайшее
повторение связанных учебных материалов. Повтор предыдущего успешного запроса идемпотентно
возвращает текущую позицию и не начисляет повтор дважды. После последнего вопроса статус становится
`completed`, причина — `finished`.

### `POST /mock-interviews/sessions/:sessionId/complete`

Досрочно завершает активную сессию с причиной `manual`. Если дедлайн уже прошёл, причина будет
`timeout`. Повторный запрос возвращает сохранённый результат без изменения причины и времени
завершения.

## Таблицы

- `users`, `auth_identities`, `telegram_link_codes`, `telegram_quiz_callbacks`;
- `user_topic_preferences`, `notification_settings`;
- `content_items`, `user_content_state`;
- `user_theory_state`;
- `study_sessions`, `study_session_items`, `answers`;
- `mock_interview_sessions`, `mock_interview_question_assessments`;
- `delivery_log`.

`delivery_log` имеет уникальный ключ пользователя, локальной даты и типа уведомления. Поля
`attempts`, `last_attempt_at` и `next_attempt_at` управляют атомарными повторными попытками:
сетевые ошибки, `429` и Telegram `5xx` повторяются с exponential backoff, а постоянная ошибка
фиксируется перед отключением канала уведомлений. Перед вызовом Telegram scheduler повторно
проверяет дневную сессию; завершённое занятие отмечается статусом `skipped` и кодом
`SESSION_COMPLETED` без отправки сообщения.
`answers.client_answer_id` обеспечивает идемпотентную отправку, а уникальная пара
`session_id + content_id` не допускает два разных ответа на один пункт сессии.
Уникальный индекс дневной сессии частичный (`kind = 'daily'`), поэтому practice-сессии не
конфликтуют между собой. `telegram_link_codes` хранит только хеш одноразового кода, дату
истечения и дату использования. `telegram_quiz_callbacks` хранит короткоживущую серверную
привязку opaque callback к конкретному варианту и идемпотентному UUID ответа.
